# ISCX-Tor2016: preprocessing protocol and every assumption in it

**Status: the loader is written but has not been run against the real
distribution.** ISCX-Tor2016 sits behind a registration form and was not
obtainable at the time of writing. Everything below is either documented by the
dataset's authors, or an assumption this loader makes that a first run must
verify. Assumptions are marked **[ASSUMED]** and each says how to check it.

## Why this corpus

It is the only dataset we found offering a grouping axis that is **neither
temporal nor per-file**. The collection captured the same activity
simultaneously at the workstation and at the gateway, releasing paired pcaps.
That gives `vantage` as a split axis, making the split-protocol comparison
three-way instead of two-way. A finding that survives a non-temporal,
non-per-file grouping is materially stronger.

## What a row is

One **conversation segment**: packets between one client-server endpoint pair
over one transport, cut by a 10 s idle timeout and a 10 s active timeout —
identical to the 5G Traffic loader, so segments are comparable across corpora.

Endpoints are canonicalised with the lower-port side taken as the server. This
is a heuristic, used **only** for flow grouping and never as a model input.

## Labels

`service` is one of eight application categories matched from the capture path
by the patterns in `CATEGORY_PATTERNS`. `app` is the capture-task filename.

**[ASSUMED] The path contains the category.** The dataset encodes metadata in
filenames and ships no manifest. *Check:* the preparer prints the service
distribution; a large `unknown` count means the patterns miss this layout.

### The labelling caveat that must reach the paper

The published procedure extracted flows from the **workstation** capture,
confirmed the majority were generated by application X, then labelled **every**
flow in the corresponding **Tor** pcap as X. Tor-side labels are inherited
wholesale from a majority argument taken at the other vantage point. They are
not per-flow ground truth, and no result on this corpus should be presented as
though they were.

## Vantage

`vantage` is `gateway`, `workstation`, or `unknown`, inferred by
`infer_vantage`. Directory components are consulted before the filename.

**[ASSUMED] The release is organised Tor/NonTor at the directory level.**
*Check:* the preparer warns if over 5% of rows are `unknown`, and the manifest
records the full distribution.

Two traps this inference had to handle, both of which the first implementation
got wrong:

- `\btor\b` does **not** match `tor_skype`, because `_` is a word character.
  Tokens are separated by `_`, `-`, `.` and `/`.
- `nontor` contains `tor`, and a NonTor capture whose filename contains
  `gateway` must not be read as the Tor vantage. Negatives are tested first and
  the directory outranks the filename.

## Capture format

**[ASSUMED] pcap or pcapng.** Sources disagree. `flowconx/data/pcap.py` handles
both, reports which it saw per capture in the manifest, and raises
`UnsupportedCapture` on anything else rather than yielding zero packets — a
loader that silently reads nothing is indistinguishable from a capture with no
matching traffic.

## What we deliberately do not use

The distribution also ships ARFF flow files with 28 time-based features. **We
ignore them entirely.** They carry no addresses and no timestamps, so no
grouped split protocol is possible on them — which is the whole point of this
project. Some descriptions of that feature set list Source IP, Source Port and
Destination IP among the columns and others describe it as time-features-only;
we did not need to resolve that, because we work from the raw captures.

## Known problems with this corpus, stated up front

1. **The non-Tor half is recycled from ISCX-VPN2016.** The two are not
   independent corpora and must never both be used as though they were.
2. **The label is a function of the filename.** Grouping on `capture_id` is not
   optional here; under a random flow split, label identity and file identity
   are the same variable.
3. **Heavy class imbalance.** Roughly 56.5k non-Tor against 11.7k Tor in the
   standard flow release. Macro-F1 and balanced accuracy are reported, and
   classes with no test support are excluded from macro averages.
4. **The capture-task design resembles our 5G corpus, not a backbone corpus.**
   Scripted per-application sessions with two users. What this dataset buys is
   the vantage structure and a documented labelling mechanism, **not** a third
   kind of collection. The paper says this rather than implying a broader
   contrast than we have.

## Running it

```bash
# after extracting the download under data/raw/ISCX-Tor-NonTor-2017/
python -m flowconx.data.prepare --source tor
python -m flowconx.audit.run_audit --csv data/processed/iscx_tor.csv --seed 42
```

The audit will report which split protocols the extraction supports. If
`vantage_disjoint` is unavailable, the vantage inference failed and the
assumptions above need revisiting before any result is trusted.
